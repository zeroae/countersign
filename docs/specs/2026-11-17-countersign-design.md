# Countersign design

17 November 2026 · Approved design · Reference implementation and operating instructions below

## Intent

A user runs a job that needs to call a protected HTTPS service. The job runs curl with ordinary proxy and trust settings. On the user's desktop, Countersign asks whether this job may use a particular installed certificate for a particular host and time. If the user approves, the site's TLS server receives a client certificate and a valid proof made with its private key. The desktop's native provider performs the signature. The remote Gateway completes the handshake and carries the HTTP traffic.

**One approval authorizes a bounded grant.** Several handshakes and requests can use that grant. Every new handshake needs the paired Companion and the selected identity. The native provider can require a PIN or touch each time. Explicit renewal requires another approval. The prompt must make the difference between one signature and a period of access clear.

### Goals, non-goals and anti-goals

- Let any Integrator operate its own Broker and Gateway, use its existing accounts and define its own units of work. One installed Companion can serve many independent Integrators. There is no central registry, account service or traffic relay.
- Support ordinary HTTPS clients, native desktop identities, administrator-defined destinations, local approval and a measurable upper bound on continued access after revocation. Support both Gateway modes in v1.
- Exclude personal key/certificate upload, key export, generic remote signing and decrypted user keys on disk. An Integrator-supplied **proxy CA** in shared mode is a separate infrastructure credential.
- Exclude transparent system-wide interception, modification of the desktop trust store, browser extensions, page-to-localhost requests, and remote content in the approval UI. Phone push, email and Slack are outside v1.
- Scope cutoff to traffic through Countersign. A website can issue a session cookie or token during a grant. Its expiry, revocation and any direct access paths belong to the website and Integrator. Workload network confinement is required if the Integrator promises mandatory proxy use.
- Ship artifacts and a local demonstration. Live deployment, production qualification of shared infrastructure, acquisition/use of signing certificates and publication to language or conda registries are outside this project phase. The owner permits temporary public visibility if needed for CI and expects the project to become public eventually.

## Roles and data flow

| Role | Responsibility |
|---|---|
| Integrator | Operates its own services. Authenticates people, authorizes their Contexts, issues Workload credentials, configures destinations and trust, and serves the widget and discovery manifest over HTTPS. |
| Workload | An agent, job or script acting for one authenticated user in one Context. It can request traffic within that binding. It cannot select its owner. |
| Context | An opaque, Integrator-scoped unit of work with an owner and lifecycle. A display label helps the person recognize it. The stable ID and current Workload instance bind authorization. |
| Gateway | Authenticates the Workload binding, enforces destination policy and leases, issues downstream proxy leaves and hosts isolated grant workers. Each worker terminates downstream TLS and establishes upstream mTLS. |
| Broker | Authority for pairing, account and Context bindings, approval arbitration, grants, validation, leases, signing relay, audit and notifications. Owns the Integrator backend API. |
| Companion | One Electron tray app per desktop session with start-at-login support. Maintains an outbound authenticated channel per pairing, presents security decisions and asks its Rust addon for scoped native signatures. |
| Web widget | A web component hosted by the Integrator. Starts pairing or Connect, reports status, opens the Companion, and registers for site Web Push. The user approves certificate use in the Companion. |

A protected request crosses two separate TLS connections. Control messages take a different route from HTTP content.

```text
Workload ── CONNECT + TLS ──► Gateway grant worker ── TLS with client auth ──► protected site
                                    │
                         auth, lease, sign operation
                                    │
Integrator backend ◄───────────── Broker ◄──── outbound authenticated WSS ──── Companion
       ▲                            │                                            │
       │ authenticated site API     └── Web Push hint ──► site service worker     └── native provider
   Web widget ── opaque-ID link ─────────────────────────────────────────────► Companion
```

## Threat model and custody

The user trusts the paired Integrator, including its Broker and Gateway. The Gateway sees plaintext in both directions and holds both legs' traffic keys. An authorized remote process can read responses, issue requests and retain information it sees. The local signature proves key possession during TLS. It cannot cryptographically constrain what a malicious TLS terminator does with the session, or independently attest the Gateway's account of the upstream peer. Show this trust relationship before approval.

Protect against another user, Workload, stale device, renderer, compromised notification channel, or isolated worker borrowing authority. Treat caller headers, labels, incoming links, theme content, DNS answers and issuer responses as untrusted. The trusted Gateway parent, Broker, desktop main process/addon, native providers, configured roots, Integrator's auth backend and host administrators are in the trusted computing base. Local administrator compromise, a compromised desktop login/provider, and resistance to an Integrator that controls the entire enforcement stack are outside the guarantee.

| Key or secret | Custodian and lifetime |
|---|---|
| Website client private key | Existing native identity. Only a selected public chain and scoped signatures cross the channel. Countersign neither creates a new copy nor promises a pre-existing identity was originally generated non-exportable. |
| Pairing key | Distinct per Integrator/account pairing, generated in user-scoped protected storage. Only its public locator, public key and binding metadata are app data. Device authentication has a separate purpose from TLS signing. |
| Proxy CA key | Sidecar parent memory for one launch, or the configured shared issuer. A Workload co-located with the sidecar shares a host kernel. UID/container isolation, mount boundaries and host hardening are part of key custody. Host root can defeat them. |
| Proxy leaf and session keys | Ephemeral, in the grant worker's memory. Never persisted, inherited by later grants or placed in logs, crash reports, swap dumps or TLS key logs. Disable dumps and require appropriate host memory/swap policy. |
| Service credentials | Restricted to the issuing backend, Gateway supervisor or Broker according to audience. Push subscription secrets and VAPID private keys are restricted service data. The widget and grant worker receive no service credential. |

## Destination policy and proxy entry

Protected entries contain a stable entry ID and version, canonical DNS pattern, numeric port, trust/validation profile, permissions and approval scope. An exact entry matches one host. Proposed wildcard semantics consume **one whole leftmost DNS label**. Thus `*.foo.bar:443` matches `api.foo.bar:443` and excludes `foo.bar:443`, `a.b.foo.bar:443`, `badfoo.bar:443` and other ports. Apply the same canonicalization in the registry, approval UI, CONNECT parser, issuer, worker and relay. Normalize case, IDNA A-labels and effective port. Reject ambiguous authorities, userinfo, IP literals, encoded separators and wildcard targets. Show the canonical A-label where a display name could be misleading.

Exact entries take precedence over wildcard matches. Reject conflicting definitions at the same precedence. Default approval scope is the exact requested host and port, even on a wildcard match. Only a wildcard entry explicitly configured for group approval may offer its full pattern. A group grant covers only hosts for which that same entry/version still wins and the user still has permission. Show the initiating exact host **and** the wildcard, port and breadth in security chrome. Key grants by the effective scope. Policy changes invalidate affected grants and pending decisions. Within a group, pin each stream, leaf, validation verdict and signing operation to one exact origin.

The default Gateway admits HTTPS CONNECT to configured destinations. Unknown destinations receive a policy denial. Integrators can arrange ordinary egress separately. A protected failure always closes or denies the attempt. The Gateway must never convert it into an opaque pass-through tunnel. At a site claiming mandatory routing, the Integrator restricts direct network access including aliases, IP literals, fronted/shared endpoints and alternate proxies. Environment variables alone provide client configuration.

Resolve the canonical host in the trusted Gateway parent. Validate the answer set against the site's address policy, normalize IPv4-mapped IPv6 and fail on mixed permitted/forbidden answers. Block metadata, loopback, link-local and infrastructure addresses. Private sites require an explicit host/prefix/port rule. Connect to the selected IP and port without a second DNS resolution, retain the DNS name for TLS verification, and repeat policy and resolution checks on reconnect. Check CONNECT authority, downstream SNI and each HTTP Host or HTTP/2 :authority for agreement. Reject conflicting absolute-form URLs, connection upgrades to unrestricted tunnels and cross-origin coalescing. Redirects require the new destination's own policy decision.

## Gateway modes and issuance

Both modes run the same proxy, admission, issuer validation, per-grant worker and lease code. Only credential delivery, ingress binding and the CA source vary.

**Sidecar (default).** Start beside a single Workload instance. Give the sidecar an Integrator-issued Workload token through its own protected credential channel. The Broker authenticates that token and derives Integrator/user/Context/Workload and generation. Bind the local proxy listener to that Workload through a private network or OS access control. This endpoint conveys that Workload's authority to its local clients. Keep credentials out of the proxy URL, tool environment and forwarded headers.

Generate a fresh self-signed CA in memory on each start. Set CA basic constraints, path length zero, certificate-signing usage and critical X.509 `nameConstraints`. Construct permitted DNS subtrees from the canonical configured names. For both an exact `api.foo.bar` and wildcard suffix `foo.bar`, encode the respective bare DNS name. The subtree includes its apex and descendants. Exclude all IPv4 and IPv6 addresses with address-and-mask subtrees for `0.0.0.0/0` and `::/0`. Name constraints express neither ports nor exact-only DNS names. The Workload client owns enforcement of name constraints on its trust anchors. Countersign owns the encoding of the extension, the Gateway’s destination checks and the issuer’s exact-host checks. Those checks apply on every connection. [RFC 5280 §4.2.1.10](https://www.rfc-editor.org/rfc/rfc5280#section-4.2.1.10)

Publish only the public CA certificate atomically on the shared volume, mounted read-only by the Workload. The env helper supplies `HTTPS_PROXY`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE` and `NODE_EXTRA_CA_CERTS` pointing at the proper listener or public trust path. Keep this trust scoped to the Workload. A change in destination policy fences the old sidecar and requires restart with a new key and public CA before serving the new policy. Sidecar exit ends issuance and live connections. A surviving copy of the old public cert cannot issue leaves.

Run sidecar and Workload as distinct principals. In containers use separate PID/mount namespaces, non-root UIDs, no tracing capabilities, runtime socket, shared writable executable paths or host mounts. The CA key has no serialization/export interface. Verify from the actual Workload principal that it can read the public cert and use the proxy, while attempts to read sidecar memory, private descriptors, credentials or private mounts fail. Inspect shared files and packaged configuration for private key material. A scan for PEM files alone cannot prove isolation.

**Shared.** Authenticate every proxy connection over authenticated transport. For stock tools a private per-Workload adapter can hold the Integrator's short-lived, Gateway-audience token and attach proxy authentication on the TLS hop. The Gateway authenticates itself to the Broker separately and obtains a Broker-authorized binding for that Workload. Validate token issuer, audience, purpose, expiry, signature, current user/Context membership and Workload generation. Use separate audiences for Broker-side redemption in sidecar mode and Gateway ingress in shared mode. Bind retries/refresh to the same live instance. Strip client-supplied identity and proxy credentials before forwarding.

The supervisor launches a fresh, low-privilege OS process per grant version with private IPC, no credentials, no other worker memory or handles, and no direct external sockets. Isolate by user principal/container or equivalent OS sandbox, including between concurrent users. Start children without inheriting the supervisor's secret address space, environment or open descriptors. The parent mediates both network legs, retains control of their closure, and authenticates IPC to the owning child. A child can request only its grant's origin-bound streams and operations. Never reuse a worker. Fence on parent/child failure and require fresh approval after replacement. Unit and integration tests exercise the actual shared supervisor and two concurrent users. Real deployment isolation requires separate qualification.

| Shared CA source | Contract |
|---|---|
| Integrator-provided CA certificate and key | Load the dedicated proxy CA only in the trusted issuer. Validate key match, CA usages, chain and validity before serving. Restrict the private mount to the issuer. Distribute only public trust to Workloads. |
| ACM-PCA-compatible issuer | Use one standard AWS SDK adapter (e.g. `aws-sdk-acmpca`). Operator config supplies region, endpoint URL or service-specific endpoint, profile/credential chain, CA ARN and template. Treat configured resource IDs as opaque and verify returned association. A profile may use `credential_process` and a named `services` section with service key `acm_pca`. This works by the same API contract for AWS Private CA and ZAE-ZCM. Endpoint or credential failure must not trigger fallback to another CA. |

The worker generates a new leaf key and CSR for an exact intercepted host. The issuer verifies CSR possession, worker and grant version, current exact host policy and deadlines. Derive leaf attributes from that authorization. Require one exact DNS SAN, matching public key, server-auth usage, non-CA constraints, expected issuer chain and bounded validity. Reject extra DNS/IP names and wildcards. A template that adds an identity URI requires an explicit profile for the exact expected URI. The URI conveys no destination authority. Apply the same returned-leaf checks to all sources.

Call IssueCertificate and retrieve the result using GetCertificate with the configured CA identifier. Bind idempotency to the same CSR, grant version, host and expiry, bound pending retries by the original deadline, and recheck grant liveness before delivering the cert. Reject backend validity rounding or templates that exceed the cap. Only the issuer holds backend credentials. Shared trust rotation stages the replacement public anchor, confirms Workload receipt, switches issuance, drains old grants and retires old trust. Compromise stops new issuance and revokes affected grants. [AWS IssueCertificate](https://docs.aws.amazon.com/privateca/latest/APIReference/API_IssueCertificate.html) · [ZAE-ZCM profile setup](https://github.com/zeroae/zae-zcm#configure-a-profile)

## Broker API, protocol and pairing

`countersign-protocol` owns versioned types and compatibility fixtures for both links. Companion connections use TLS-verified outbound WSS with subprotocol `countersign.v1`. A Gateway uses a separately authenticated TLS channel to the Broker for binding, approval, grant lookup/activation, lease renewal, sign/cancel and status. Each message carries a version, typed operation, fresh request ID and bounded body. Reject duplicate keys, unsupported versions/types, invalid encodings, excess nesting and oversized frames before dispatch. Proposed v1 limits are 1 MiB per uncompressed JSON frame, 16 public DER certs/256 KiB total chain and 256 KiB signing input. Disable compression. Provide heartbeat/idle limits, bounded reconnect backoff and independent authentication at upgrade.

The backend API uses distinct service credentials for an Integrator. Browser calls go through its authenticated same-origin backend, which derives the account and verifies Context ownership, CSRF token and Origin before invoking Broker operations. Operations include start/confirm pairing, list/forget devices, Connect/retry/renew, status/revoke, register/delete push subscriptions and close a Context or Workload. Account blocks, destination permissions, policy updates, issuer stop and emergency stop require administrator authority. Scope every lookup, including status, by authenticated owner. IDs correlate records. Knowledge of an ID confers no read or mutation access.

| Exchange | Binding and effect |
|---|---|
| Pair / authenticate | Verified Integrator origin, paired Broker endpoint, account, device/key, version, purpose, attempt or connection, random challenge, issuance and expiry. |
| Notify / fetch / offer / decide | An opaque ID wakes the client. Authenticated fetch returns request/version, user, Context, Workload generation, initiating host, allowed scope, duration bounds, policy and a device/channel-specific offer. A decision binds that offer, selected chain/fingerprint and duration. |
| Activate / retire | Supply grant ID/version, winning pairing, local selection, allowed scope, user, Context, Workload and worker generation, validity and policy versions. The Companion checks the match to its own recorded approval before enabling signing. |
| Lease request / reply | Full scoped binding, enforcer identity and generation, fresh request/sequence, decision, remaining budget and absolute caps. |
| Sign / result / cancel | Full activated binding plus exact host:port, TLS connection and operation IDs, channel generation, TLS version/scheme, rustls signing input and deadline. Response correlates to that exact operation and is consumable once. Cancellation is idempotent. |
| Status / security event / revoke | Authenticated owner, affected versions, event ID, reason and authoritative disposition. Delivery, remote authorization and actual cutoff are distinguishable outcomes. |

Pairing begins with an explicit verified HTTPS Integrator origin and a fresh local P-256 key. Proposed v1 ingress exposes the Broker under the Integrator origin through reverse proxying. This gives enrollment, manifest fetching and the WSS route a common verified origin without trusting a theme-provided endpoint. Open the real Integrator sign-in in the system browser. A ten-minute pending attempt binds the key and origin. Show matching verification codes derived from the attempt/key in the browser and Companion, plus account, origin and device. Require authenticated browser confirmation and proof of the exact pending key before committing. Bind both halves to the same attempt under a single-use transaction. A link, device label or intercepted code alone cannot enroll a device.

Sign a fresh, single-use challenge (at most 60 seconds) on enrollment and every reconnect. Use purpose-specific ES256 JWS with fixed algorithm, type, audience and connection binding. Verify against the server-held key and attempt, reject embedded alternative keys and fence the previous generation only after successful proof. One connection is current per pairing. Reconnect cancels old operations, fetches fresh state and reconciles locally approved scopes. Persist only protected/integrity-checked local approval receipts needed to restore authority, bound to pairing, cert and absolute expiry. A missing receipt requires fresh approval. Unpair/lost key requires new enrollment and grants.

## Approval, signature and lease lifecycle

1. A protected CONNECT or an explicit widget Connect requests the same authority. Broker validates the binding and coalesces matching pending requests by owner, Context, Workload generation, effective scope and policy version. Preserve the initiating host in the offer. Pending approval lasts ten minutes. A CONNECT waits at most two minutes total, further capped by caller and authority deadlines. Disconnecting a waiter discards its traffic. The user can approve for a later deliberate retry.
2. Broadcast an ID to all eligible connected pairings for that Integrator/account. An offline paired device can authenticate and fetch a still-pending offer. A device with no eligible identity reports local unavailability. Zero devices means unavailable or awaiting a paired device, with a bounded wait. The user's explicit Deny/Cancel resolves the request globally. Dismissing a notification only dismisses it locally.
3. The user reviews the available certificates in the Companion and chooses the certificate and duration for this grant. Start the absolute grant lifetime at approval commit. Use one hour by default and an administrator-configurable maximum initially eight hours. Show absolute expiry, capped by certificate expiry. Before commit validate user, Context, destination permission, policy version, pairing, channel generation, selected chain and current request. First valid terminal decision committed wins, including denial, cancellation and expiry. Atomically compare-and-set pending version, insert at most one winning grant and audit/outbox, then notify losers to close prompts. Identical retries return the committed result. Reject changed payload under the same decision ID. No signer election after a failed handshake.
4. Bind the grant immutably to Integrator, user, Context, live Workload instance/generation, resolved approval scope and policy, winning pairing/key and selected leaf SHA-256 fingerprint. Bind its worker exactly once on activation. Maintain one current version per binding/scope. Denied/cancelled/expired prompts suppress repeated automatic requests until explicit retry. A renewal creates a newly approved grant and fences the old; failed renewal leaves the original deadline intact. Warn five minutes before expiry when possible. Report approved, ready and upstream mTLS accepted as distinct observations.
5. Acquire valid leases before opening protected traffic. The worker accepts only its scoped downstream stream, obtains an exact proxy leaf, and drives rustls on bounded handshake threads. Independently verify the upstream chain, name, server's TLS proof and required validation evidence before dispatching any client signature. Treat an unverified CertificateRequest as a hint. Require initial-handshake client auth and fail if the upstream did not request/use the approved identity. A verified peer that requests no certificate cannot produce a successful protected connection.
6. Route the signing operation only to the winning device. The addon checks the live, locally approved scope, device/channel, exact host match, selected native identity, scheme, operation and deadline. It signs the rustls CertificateVerify message via the provider with exactly the hashing and encoding required by that scheme. The worker verifies the returned signature under the approved certificate and consumes it once. Provider dialogs can recur. Fail closed on token removal, mismatch, cancellation, late results and invalid signatures. Closing the Companion cancels pending handshakes. Established HTTP connections can continue while every remote validity condition holds.
7. Keep streams, TLS keys, peer state, buffers and connection pools private to one grant version and exact host. Disable TLS resumption/tickets on both legs, early data and HTTP/2 cross-origin coalescing in v1. No shared cookie jar. Stream HTTP/1.1 and HTTP/2 with backpressure and per-request authority checks, including streams opened on an existing connection. Never automatically replay a timed-out or partially sent application request.
8. Explicit revoke/unpair, Context closure, Workload replacement, known certificate revocation, account block, permission withdrawal and emergency stop invalidate affected grants. Retire local scopes, cancel signatures and fence both traffic legs. Replacing a cert, device or grant requires new approval. The Companion distinguishes a queued offline revoke intent from Broker commitment and confirmed enforcement.

Multiple devices may be connected to the same account. Warn existing and new devices, name the devices, time and trusted-ingress-observed address with provenance if available. Display labels as user supplied. Distinguish presence, observed identical public certs, and verified use on multiple devices. Neither observation proves key copying. “Disconnect other devices” confirms named targets, atomically forgets those pairings, invalidates offers and revokes their grants. Exclude the actor and reject changes to the confirmed target set. Preserve a restricted security notice for offline users after reauthentication and a tombstone for fencing.

### Authoritative leases

The trusted downstream ingress, upstream socket relay in the Gateway parent, and Broker signing relay each enforce authority independently of worker cooperation. Each obtains a scoped lease from the authority or, for the co-located signing relay, from the same transactional authorization check. An enforcer which has not obtained a lease cannot admit or continue work. A grant may last hours. Each lease has a 30-second maximum budget with renewal attempted every ten seconds.

Anchor the budget at the enforcer's monotonic **request send time**. Use the earliest of that budget and the conservatively translated absolute grant, credential/binding, certificate and validation deadlines. Subtract bounded clock uncertainty. Reject late, stale, swapped, out-of-order and wrong-generation replies. Uncertain clock, suspend or lapsed authority causes immediate cutoff and fresh validation before any subsequent connection. Broker renewal checks all current state, including revocation and stop, in one snapshot. Push invalidations accelerate cutoff. A lost push or dead Broker cannot keep an old lease alive.

On expiry stop admission and forwarding, reset HTTP/2 streams, close active and idle sockets in both directions, discard buffered work, cancel queued/native operations and retire capabilities before cleaning up the child. Bytes already delivered to the peer are beyond recall. A blocked provider call retains its slot until it returns, and its late result is discarded. A worker ignoring cancellation cannot keep either socket open. Measure final admitted traffic and actual closure under load and scheduler delay. Thirty seconds is a design bound on issued authority. End-to-end enforcement timing needs measured evidence.

Initial admission limits per user are eight grants, 128 connections/streams of each kind and sixteen concurrent handshakes. Per grant allow 32 connection pairs, 32 in-flight requests/streams and four handshakes. Limit application buffering to 1 MiB per pair. One provider call executes at a time per device across pairings, with sixteen queued and at most four from one grant. Queue time counts toward the original two-minute operation deadline. Apply per-account and deployment caps to pending offers, notifications and unauthenticated enrollment. Return a stable safe code and correlation ID for policy denial, authentication required, overload, unavailable, elapsed wait or TLS failure. After TLS/HTTP commitment close the affected stream and publish status through the owned API.

## Native identities and certificate validation

`countersign-native` is a Rust napi-rs addon loaded only by Electron main. The renderer runs packaged local content with sandbox and context isolation enabled, Node disabled, a restrictive CSP and a narrow preload API. Validate the frame, sender and action on every IPC call. Renderers can request a list of eligible public identities, confirm a selection or cancel an offer. The Companion lists every installed certificate eligible for this request. Each entry shows the identity, issuer, expiry and SHA-256 fingerprint so the user can distinguish certificates with the same display name. With two or more eligible certificates, require the user to select one before enabling Approve. With one, show it for approval. With none, explain why approval is unavailable. Provider handles stay in Rust. Re-resolve short-lived selection references and verify the fingerprint at approval and use. Keep discovery local. Send the selected public leaf and needed intermediates only. Distinguish missing intermediate, no eligible certificate, locked provider, PIN cancellation and device removal. Never substitute a different certificate on failure.

| Platform | Website identity | Pairing protection and evidence required |
|---|---|---|
| Windows | Current user's certificate store and CNG signing provider. Build the selected public chain, respecting supported KU/EKU, issuer and schemes. | Persistent user-scoped non-exportable CNG P-256 key, with OS protection such as DPAPI for app-owned sensitive metadata. Prove restart/reopen, non-exportability and denied cold access. |
| macOS | Security.framework identities in the user's Keychain, using SecKey signing and provider-mediated interaction. | Keychain-protected app-owned P-256 key with access control and non-exportability where supported. Prove reopen, denied access and prompt/cancel with the artifact for which support is claimed. |
| Linux | Explicitly configured PKCS#11 providers exposed through p11-kit/NSS. Enumerate eligible installed identities and sign through token sessions. | Candidate is a persistent non-extractable NSS softoken key with a nonempty random token password in an encrypted Secret Service collection. Prove actual backend protection, unlock, persistence and locked cold reopen. Linux ARM64 and x64 software-provider runs cover this GNOME profile. |

Preserve the OS/provider's PIN, touch and unlock UI. Perform blocking operations off the JavaScript event loop on bounded native workers. Open handles can survive a keyring lock. For the Linux cold test close sessions and erase cached unlock material first. Restart both app and provider services, check identical public identity after user unlock, and fail closed on lock, cancelled unlock, missing provider or corrupt locator. In CI provision an encrypted GNOME Keyring over private session D-Bus and deliver the simulated user's unlock via an in-memory pipe. No unlock secret in argv, environment, files or logs. Other desktops, providers and hardware require their own rows. Windows and macOS qualification proceed independently of Linux.

The addon exposes separate typed operations for pairing key create/reopen/proof/retire and local TLS scope activate/sign/cancel/retire. Bind native authorization to trusted main-process approval and Broker activation. Limit inputs to the supported CertificateVerify form/version/scheme. TLS 1.3 uses the client context string; TLS 1.2 requires the handshake transcript for the selected connection. TLS ECDSA signature encoding differs from the fixed-width JWS ES256 representation. There is no general sign-bytes export. Fixture installation or synthetic activation belongs to a separate test artifact with a nondefault build switch and a production-build exclusion. Release builds reject fixture composition at build time. CI loads real default, fixture and packaged addons to check visible exports and inspects native artifacts and service dependencies. Runtime input, environment or a renderer action cannot enable a test signer in a distributed artifact.

Prefer TLS 1.3 and support secure TLS 1.2 initial-handshake client authentication. Target RSA 2048+ with PSS, tested TLS 1.2 RSA PKCS#1 schemes, and ECDSA P-256/P-384 with SHA-256 or stronger. Require compatible provider, peer and rustls capabilities. Exclude obsolete signatures, post-handshake auth, renegotiation, HTTP/3 and clients requiring the upstream's pinned certificate from the initial profile. Empty acceptable-issuer hints do not disqualify every candidate. [TLS 1.3 CertificateVerify](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.3)

Broker policy binds trust and optional account-to-certificate mapping to the destination. Validate both the selected client chain and destination chain for their role, validity, usages and configured trust. Independently validate the upstream host and server signature in rustls. Configure revocation evidence per site. For strict profiles verify complete signed direct CRLs or signed OCSP including responder authorization, cert match and freshness. Reject unsupported extensions/forms, invalid signatures, unknown status and indeterminate required evidence. Use configured retrieval routes or verified imports only. No arbitrary certificate-supplied URL fetch. Absent OCSP nextUpdate requires a configured maximum age anchored to signed times. Scope verdicts to role, exact host where applicable, chain digest, trust/policy version, owner/grant and operation. Cap leases by verdict validity; cached evidence never gains lifetime on reuse. Known revocation invalidates. Stale required evidence cuts traffic until fresh validation. No implicit trust in the desktop's server roots.

## Companion branding and notification channels

At pairing fetch `https://<integrator>/.well-known/countersign.json` over validated HTTPS from the verified Integrator origin. Proposed manifest fields are schema version, plain-text display name, same-origin raster logo reference, accent/background colors, an optional dark-mode accent/background pair (`colors.dark`) and optional plain-text explanatory copy. The manifest carries only hex colors and the PNG logo: no CSS, fonts, SVG or HTML. Bound lengths, image bytes/dimensions and allowed color syntax; reject active content, redirects to other origins, markup, CSS, scripts, navigation and bidirectional control characters. Decode images to bounded local assets. Cache the normalized manifest, decoded logo, content digest and verified origin in the pairing. On a malformed/unavailable theme use neutral branding and show the verified origin. Refetch on reconnect with rate limits. A content change, including changed dark colors or logo bytes at the same URL, produces a visible old/new review. Keep the accepted version until the person accepts the change. The person can also keep the current branding, which dismisses that proposal until the content changes again.

Only the authenticated receiving pairing selects its theme. Neither a request field nor a deep link can choose an origin, logo or copy. While that pairing's request, pairing confirmation or detail view is on screen, the whole Companion window takes its theme: header band, window background, surfaces, borders, tabs, links, focus ring and the Approve fill. Lists, settings and pairings without a manifest use the Countersign theme. The main process follows the OS light/dark appearance and sets the window background from the stored theme of the pairing on screen, never from a renderer-supplied color. Derive the palette from the manifest colors in OKLCH and clamp lightness until every text and control pair meets WCAG AA in both appearances. The renderer receives validated hex values only and applies them as CSS custom properties under the existing CSP. The header shows the logo, display name and copy; the logo never appears in the content area beside the decision.

Fixed in every theme, never themeable: (1) a countersign mark on a fixed plate at the bottom right of the window; (2) the verified origin beside the display name, which never appears alone; (3) the request facts, account, Context, exact host:port and approval scope, always present in the same order and wording, in clamped colors; (4) warnings and errors, including a broader wildcard scope, an unavailable provider, a certificate that ends access early and no eligible certificate, as a fixed component with an icon and fixed colors; (5) **Deny / Approve** with fixed labels, Deny first, equal size and Deny outlined; (6) certificate identity, issuer and fingerprint, effective duration and expiry, and the gateway trust disclosure at full contrast; (7) when the queue moves to a different pairing's request, a fixed banner naming its origin, with Approve disabled for about a second and the reason shown. Requests appear one at a time, oldest first, with a count of the rest. No theme value can change labels, order or visibility, or cover, resize away, recolor or rename security controls. A long name, low-contrast color or logo resembling a button must leave the security decision legible and accessible. Theme data never reaches notifications.

The approved prototype is in [mockups/companion-theming](mockups/companion-theming/). Its **Middle ground** mode is the design; see [mockups/README.md](mockups/README.md).

All three notification paths carry only an opaque high-entropy ID as application payload. Transport routing/subscription data remains necessary. No authority, certificate, host, Context, theme override or callback URL travels in a notification.

| Channel | Delivery and behavior |
|---|---|
| Persistent outbound connection | Broker sends an ID over the authenticated pairing. Companion can display a generic OS-native local notification. Fetch offer details through the live authenticated channel, including on click. Only the Companion approval window can grant. |
| Widget deep link | A user gesture opens `countersign://approve/<id>`. Validate exact scheme, verb, length and ID syntax. Hand off to the single running app instance. On cold start reconnect and sync each pairing's own pending inbox. Match the ID locally to an authenticated offer, then fetch on that pairing. Never send the incoming ID to unrelated Brokers. Unknown, ambiguous, expired or inaccessible IDs produce no actionable prompt. |
| Integrator site Web Push | With user permission, the site's service worker registers a subscription through the authenticated backend. When the Companion is unavailable, the Broker's VAPID-authenticated sender encrypts an ID-only payload to that user's site subscription. A generic notification click opens the same-origin site, whose widget can launch the Companion. Offline delivery remains best effort. A click, wakeup or service-worker event cannot approve a grant. |

Bind subscriptions to origin/account, handle logout, deletion and gone endpoints, bound retries by request expiry, and deduplicate wakes by ID. Validate push endpoints against the Integrator's allowed HTTPS push services and address policy to avoid turning registration into an outbound request proxy. Keep subscriptions/keys out of logs. The widget can display status if launch or Push permission is unavailable. Appearance via CSS custom properties affects only web content. The Companion never accepts commands through a loopback HTTP listener. [Web Push protocol](https://www.rfc-editor.org/rfc/rfc8030)

## Persistence, recovery and audit

`countersign-broker` uses a storage trait whose methods represent atomic domain operations such as consume challenge, settle approval, renew lease and revoke pairing. SQLite is the reference implementation. Use foreign keys scoped to Integrator/user, unique pending and active-scope constraints, decision idempotency keys and versioned compare-and-set updates. Transactionally couple authorization mutations, restricted audit and a delivery outbox. Competing connections/processes observe the same winner. Outbox consumers can retry idempotently after a crash. A failed audit/authority transaction cannot create a grant. An unavailable database cannot delay local deadline enforcement.

Persist policy and permission versions, pending challenges/offers and deadlines, pairing public keys and generations, approval outcomes, grant bindings, scoped public chains/verdicts, subscription data, security notices and minimal revocation tombstones. Keep traffic keys, TLS sessions, native handles, signing messages/signatures, HTTP content, authorization headers, paths and cookies out of storage and logs. Audit actor, transition, scope IDs, exact origin, fingerprint, timestamps, result and correlation ID. Restrict identifying metadata, including network observations, to authorized views. Record enforcement acknowledgments separately from revocation intent and notice delivery.

Bound retention per Integrator. Immediately make ended grant data unusable for authorization, then remove working chains and expired transient records with retryable cleanup. Preserve a minimal suppression marker for explicit-retry behavior during the relevant Workload lifetime. On restart fence stale generations, expire pending work, reauthenticate channels and reconcile absolute deadlines. Restore of a database backup requires a fresh authority epoch and invalidation of old live grants/challenges, including reconciliation of pairing revocations before accepting devices. Never restore old worker state or assume an outbox delivery proves cutoff.

### Configure an Integrator

1. Give the Broker a TLS server certificate, key, SQLite path, independent backend credential, Workload HMAC key and client trust anchors. Set `origin` to the public Integrator authority including its port. Set `listen` to the private listening address. Publish the exact WebSocket path `/v1/companion` under the Integrator HTTPS origin. Forward WebSocket upgrades with the `countersign.v1` subprotocol. Keep backend, admin and Gateway endpoints on authenticated service paths.
2. Serve `/.well-known/countersign.json` over HTTPS. A minimal manifest is `{"version":1,"displayName":"Example","colors":{"accent":"#164e63","background":"#ffffff"}}`. Optional fields are `copy`, `colors.dark` with its own `accent` and `background`, and a same-origin PNG `logo` URL. The Companion pins the origin at pairing and asks the user to accept later branding changes.
3. Register destinations in both processes with matching IDs, versions and patterns. For group approval set `whole_wildcard: true` in the Broker and `approval: "whole_wildcard"` in the Gateway. The default is one exact destination. Each Gateway entry has a `roots` PEM path for upstream server authentication. Internal destinations require an exact entry and explicit `private_networks` prefixes. Broker `client_ca_file` supplies the default client trust. Per-entry `client_trust` accepts `ca_file`, `user_fingerprints` and a revocation profile. The Gateway also accepts a per-entry `revocation` profile. CRL and OCSP files are bounded administrator-imported DER objects.
4. Start the Broker with `countersign-broker broker.json`. Authenticate users in the Integrator. The backend mints short-lived Workload credentials by posting the server-derived binding to `/v1/backend/workloads`. Write the token to the Gateway's protected credential path and refresh that file atomically. Put the sidecar listener on an endpoint reachable exclusively by its Workload.
5. Run `countersign-gateway serve gateway.json`. Deliver the four exports from `countersign-gateway env gateway.json` to the Workload. Mount the public CA at the same path read-only. On changes to destination rules, retire existing authority, update the version in both service configurations, and restart the sidecar.
6. Load the web component in the authenticated site and set its `adapter`. The required `pair()` starts the pairing flow and `connect()` returns a request ID from the backend. Optional `subscribe()` registers site Web Push on a user gesture. To enable Web Push, configure Broker `web_push` with an exact `allowed_hosts` list, a `mailto:` contact and a private `vapid_key_file` containing a base64url-encoded 32-byte P-256 scalar. Supply the matching public application-server key to the site's PushManager. Delete the subscription on logout. [Example adapter and session handling](../../examples/demo-integrator/site/app.js) · [Reference backend](../../examples/demo-integrator/integrator.js)

The example launcher constructs complete Broker and Gateway JSON configurations with fresh deployment-specific values. The Rust config types define all supported fields. [Broker config](../../crates/countersign-broker/src/config.rs) · [Gateway config](../../crates/countersign-gateway/src/runtime/config.rs)

**Shared Gateway.** Configure `shared.listener_cert`, `shared.listener_key`, `shared.gateway_token` and `shared.ca`. Omit the sidecar's `workload` and `workload_token` fields. Supply an HTTPS proxy URL. The Integrator backend requests `mode: "shared"` credentials and the Workload or its private adapter sends a single `Proxy-Authorization: Bearer` header on the encrypted proxy connection. For a local CA, use `{"type":"local","cert":"/run/issuer/chain.pem","key":"/run/issuer/key.pem"}`. Place the issuer first and trusted root last in that certificate bundle. For remote issuance, use the standard AWS SDK configuration below. Set the authority and template to values supported by your issuer. Select a signing algorithm that matches its CA. The template must issue an exact-host server leaf within the absolute expiry. A backend adding a single required URI SAN can be configured with `expected_uri`.

```json
{
  "type": "acm_pca",
  "region": "us-east-1",
  "profile": "proxy-issuer",
  "ca_arn": "<issuer authority identifier>",
  "template": "<issuer template identifier>",
  "signing_algorithm": "SHA256WITHECDSA",
  "roots": "/run/issuer/roots.pem"
}
```

An explicit HTTPS `endpoint` overrides SDK endpoint discovery. The shared AWS profile can supply a credential process and a named `services` block with an `acm_pca.endpoint_url` entry. The worker receives validated public leaves and holds its own leaf private key. The supervisor owns issuer credentials. [Issuer implementation and SDK fixture](../../crates/countersign-gateway/src/shared_issuer.rs) · [ZAE-ZCM profile example](https://github.com/zeroae/zae-zcm#configure-a-profile)

**Device and grant operations.** The backend uses a private Bearer service credential for `/v1/backend/*`. The browser receives a session cookie and a CSRF token. Derive the user and Context before calling `pairings/confirm`, `requests`, `status`, `renew`, `revoke`, `devices`, `pairings/forget`, `contexts/close` or `workloads/retire`. Status distinguishes the approval outcome, current Companion readiness and historical upstream mTLS acceptance. The assigned Companion can queue revocation offline and checks the authenticated Broker acknowledgment on reconnect. Issued leases bound the remaining forwarding interval. Administrative `/v1/admin/control` accepts account blocks, per-user destination denials, issuer stop and emergency stop with an independent admin credential. The default audit retention is 30 days. [Service routes](../../crates/countersign-broker/src/service/mod.rs) · [Control formats](../../crates/countersign-broker/src/service/controls.rs)

**Recovery.** Stop the Broker before restoring a SQLite backup, then run `countersign-broker --recover-backup broker.json`. This invalidates prior device and Workload authority and places the service under emergency stop. Reconcile current permissions and revoked users before clearing the stop. Users re-pair and obtain fresh approvals. A normal Broker restart also requires fresh Workload credentials. [Maintenance and recovery](../../crates/countersign-broker/src/service/maintenance.rs)

**Linux desktop.** Configure website tokens via p11-kit, or point `COUNTERSIGN_PKCS11_MODULE` to the absolute path of the operator-selected module. Tokens with a protected authentication path own their prompt. The software-token integration retrieves its unlock credential from the encrypted login collection using attributes `application=Countersign`, `kind=website-token`, `token=<token label>`. Pairing uses non-extractable NSS keys with a separate random unlock secret. “Start at login” is available in the packaged Companion.
